# 认知掌控侧车（Cognitive Sidecar）

> **当前状态（2026-11-10）**：依托本机 Python / `.bat` / agent 环境的开发态已归档删除，
> 唯一可运行形态是 `认知掌控侧车-独立版/` —— 双击 `启动.vbs` 即可，自带运行时、不联网、
> 整个文件夹拷走就能换机器。`sidepanel-extension/` 插件仍可用，它连的是独立版起的 8501。
> 开发态源码、构建脚本、测试与历史数据已完整备份在 `开发态备份-2026-11-10.zip`。
> 下面第 1 节、8.5–8.7 节描述的是开发过程与实现细节，作为历史文档保留。

一个跑在本地的旁路工具：**不改造工作 Agent**，只在它旁边帮你做三件事——

1. 把它吐出来的结果翻译成你能判断的**结果程度卡**（完成度 / 确定性 / 疑点 / 偏差 / 下一步）；
2. 把你模糊的偏好沉淀成**可编辑的规则**，并在每次审批时告诉你“按哪条规则判的”；
3. 在澄清之后给你一张**结构化委托卡**，你手动复制给工作 Agent。

方向盘始终在你手里：侧车只给依据和选项，接受 / 驳回由你点。

## 1. 五分钟跑起来

```bash
pip install -r requirements.txt

python demo.py            # ① 不开界面、不联网，跑完整个闭环并自检
python -m streamlit run app.py   # ② 打开界面（同一份数据）
```

`demo.py` 会打印每一步的落库结果，并在最后打十条自检。看到的应该是全 ✓。它已经把数据写进
`data/app.db`，所以接着打开界面，历史会话、结果卡、规则都在里面。

第一次跑想从干净状态开始：`python demo.py --reset`。

## 3. 走完一次闭环（不用读代码）

1. **工作台** → 在输入框写一句模糊构想，点「开始澄清」。
   例：`帮我做个个人网站，展示我的研究方向，最好让人一眼看出我在做什么。`
2. **回答 5 个问题**。右侧「待澄清槽位」会实时显示还缺什么。
   每轮只问一个缺口：目标 → 交付物 → 成功标准 → 边界 → 禁止项。
   - 成功标准必须 ≥3 条，且每条都要有验证方式（模型会从你的括号说明里抽取，你也可以在委托卡里改）。
3. **委托卡**出现。点 `code` 块右上角的复制按钮，粘给工作 Agent。
   想改就直接在下面「编辑委托卡」里改，保存会生成新版本（旧版本保留在库里）。
   点「定稿，去贴结果」。
4. **把 Agent 的输出原样贴回来**（不要改写、不要摘要），点「发起审阅」。
5. **侧车主动开口**。它不再吐一张表格，而是像刚看完东西的同事一样跟你说话：
   先给结论（完成度 / 确定性 / 偏差，一行数字条），再讲 1~2 个核心疑点，
   然后说清有哪些待办、哪一处要你拍板。
   每段话下面挂一颗「依据」——点开就是这段引用的原文片段（带高亮和字数定位）。
6. **你可以直接回它**，比如「第二个疑点不用管，那个是我允许的」，
   或者「决策那条我选先修移动端排版」。它会：
   - 把那一条标成「已排除」/「已定」，并留一句理由；
   - 若这句话含一条普遍适用的偏好，顺手沉淀成规则（`source=chat`）；
   - 给出下一步建议，并把「接受 / 驳回 / 打包成补充说明 / 挑一条开新会话」做成胶囊。
7. **要结案**：点「接受这次结果」；或者先在输入框写理由再点「整体驳回」，
   理由会被转成规则写进规则库，页面当场就能编辑、归档、删除。
8. **点「打包成补充说明」**，你会拿到一段已经整理好的话（已排除的、已定的、还欠的、
   验收口径），直接复制给工作 Agent，比你自己重新描述一遍快得多。
9. **下一次**贴新结果时，新规则会进入候选并被引用 —— 这就是闭环。

> 完整结果卡没有消失：对话末尾有「展开完整结果卡」，四格标尺、全部条目、
> 规则引用、成功标准逐条判定都在里面。对话负责让你看懂，卡片负责让你核对。

### 审阅对话是怎么做到“像人说话，又能逐句核对”的

一句话：**骨架由代码拼，措辞由模型改，越界的段落直接丢。**

1. `core/narrate.py` 从 `reviews` / `findings` 里抽出 5 段事实，每段绑一个 `ref`
   （`verdict`、`doubt:12`、`decision:15`…）；
2. 模型只被允许改写这些段落的措辞，不许新增、不许换 `ref`、不许改顺序；
3. 返回后校验 `ref` 是否在允许集合内 —— 越界的段落丢弃；
   如果剩下的段落太少，整段退回代码拼的骨架（所以你永远不会看到空白气泡）。

所以气泡里每一句话都能点开看依据，而不是“模型说的”。

### 想试“跳过”这条路径

澄清阶段右侧有「跳过槽位」：勾选 + 写原因 + 确认跳过，或一键「把剩下的全部跳过，直接出卡」。

跳过的后果是明码标价的：

- 跳过任意槽位 → 确定性上限压到「推测」，卡片顶部挂「低置信结果卡」徽标，并在
  「为什么确定性是…」里逐条写明是哪一项被跳过；
- 跳过成功标准 → 完成度显示「无法核定」，确定性压到「存疑」。

侧车不会因为你跳过就假装一切正常。

## 4. 每个疑点的追溯依据在哪看

三道闸门，逐级降级，都写进 `findings` 表：

| 闸门 | 判据 | 界面上怎么写 |
|---|---|---|
| 精确命中 | 归一化后能在原文里 `find` 到引文 | 「逐字命中」+ 第 X–Y 字 |
| 局部窗口近似 | 用引文头/尾做种子定位候选起点，只在候选点附近开窗比对，相似度 ≥ 阈值 | 「近似匹配」+ 相似度数值 |
| 都不中 | — | 移出疑点区，进「未锚定的条目」折叠区 |

**看的地方有四处：**

1. **审阅对话的气泡里** → 每段话下面那颗「依据」，点开就是：追溯依据（第 X–Y 字）、
   带黄色下划线的高亮原文、命中方式；靠规则判的会显示「依据规则：R-003 …」。
   这是主入口：你读到哪句起疑，就在哪儿点开，不用去别的页面找。
2. **完整结果卡里点开任一疑点** → 同样的内容，外加严重度、归属分支。
3. **「结果卡」页 → 原文对照 标签** → 整篇 Agent 输出 + 所有疑点位置的高亮。
   没被高亮的地方，就是模型没给出处的段落。
4. **「规则库」页 → 展开某条规则 → 「查看命中记录」** → 这条规则在哪些次评审里被引用过、判断理由是什么。

锚定失败不是“悄悄丢掉”：卡片右上角「疑点」格会写「N 条未锚定」，红色。

**为什么必须这样**：如果疑点不能钉回原文，侧车自己就成了黑箱，你只是把“看不懂 Agent”换成了“看不懂侧车”。

模糊匹配阈值在设置页可调（0.50–0.95，默认 0.75）。调高更严：更多疑点会被判成“未锚定”；
调低更松：原文被改写也能对上，但可能对上不该对的段落。

## 5. 待办与决策分支（对话里也在讲）

结果卡不只告诉你“这版行不行”，还告诉你“下一步该干什么”。四格标尺下面是「待处理分支」：

| 类型 | 是什么 | 首屏最多显示 |
|---|---|---|
| 待办 `action_item` | Agent 没做、但你必须自己做的事 | 2 条（其余折叠） |
| 决策 `decision` | 两条以上互斥路线、选择权在你手里的地方 | 2 条（选项默认收起） |

每条只露一行：**标题 + 锚定徽章 + 三个按钮**。

- **依据**：展开这一条的判断理由，以及它引用的原文片段（带高亮）或规则。
  待办/决策和疑点共用同一套锚定：逐字命中 / 近似匹配 / 引用规则 / 未锚定。
- **回溯原文**：只读动作，把这条标成「已回溯」，同时展开依据。不新建任何东西。
- **以此新建会话**：把这条待办/决策单独开成一个新会话去澄清。
  新会话会带上 `parent_review_id` / `parent_finding_id`，下拉里显示「↳」，
  页头写着“承接自结果卡 rv-xxx 的第 N 条分支”。**有意的分叉必须留血缘**，
  否则你会分不清“我自己开的”和“界面把会话弄丢了”。

决策条目点开后会给出 2~4 个选项，每个都标了代价，另加「记下选择」。
记下只写 `state=decided` + `chosen`，**不会自动改委托卡** —— 改卡还是你自己动手。

未锚定的待办/决策不会进首屏，收在「未锚定的待办/决策」折叠区。
它们不参与确定性降级：待办是建议，不是结论，让它拉低整张卡的置信度没有道理。

> 第八节 8.7 是这套机制的进阶用法：每条待办/决策都能拉成一支**独立对话**，
> 上下文自动带上委托卡和原文锚点。这里的「以此新建会话」是另一件事 ——
> 那是换到工作台重新立项，见 8.7 末尾的对照表。

## 6. 对话连续性与草稿

### 会话不会再自己分叉

三个曾经会分叉的地方，现在都收紧了：

| 原来 | 现在 |
|---|---|
| 建会话 → 调模型，模型挂掉会留下一条“只有构想、没有问答”的空会话 | 失败就把会话标成 `aborted`，从下拉里消失（设置页能看到，也留着你写过的字） |
| 用户消息先落库，模型再挂 → 库里留一条没人接的发言 | 失败也补一格 `kind='failure'` 的说明，`user / assistant` 严格交替 |
| 输入框 key 固定，A 会话没发出去的草稿会出现在 B 的输入框里，直接提交就进了 B | 所有输入 key 带会话维度（`answer:s-xxx`），A 的草稿不可能出现在 B |

`messages` 表加了一列 `round_no`：`brief` 记第 0 轮，之后每问一答共用一个轮次号。
同一会话的历史就是一条连续的记录，界面每次 rerun 都从库里全量重绘，不做任何“追加”。

### 草稿存在库里，不在会话状态里

写了一半的构想、没发的回答、粘了一半的结果，都可以直接切页面、关浏览器。

- **存哪**：SQLite 的 `drafts` 表（`scope / key / content / updated_at`）。
  Streamlit 在控件卸载时会删掉它的 key，所以放 `session_state` 一定会丢 —— 这是实测过的。
- **什么时候存**：两条通道。① 输入框失焦时（`on_change`）立即写库；
  ② 每次页面重绘开头，把还残留在会话状态里的输入内容再刷一遍库 ——
  补的就是“打完最后一个字直接点侧栏导航”那道缝。
- **怎么回填**：渲染输入框之前先把库里的值塞进控件 key，之后只传 `key` 不传 `value`。
- **什么时候清**：提交成功后立刻删。设置页有「清空全部草稿」和草稿字数统计。

## 7. 规则是怎么被选中的

不用向量库，只用可解释的两步：

1. **预筛**：规则必须 `status=active` 且 `scope ∈ {review, both}`；对每条规则算“关键词在
   委托目标 + Agent 输出里命中了几个”，只保留命中 > 0 的，按命中数降序取前 10。
   （不做时间衰减、不做命中次数加权 —— 否则用过的规则会自我强化，越用越容易被引用。）
2. **模型复核**：把这 10 条（只给 id + 文本）交给模型，它只能返回这些 id 里的，
   并给出 satisfied / violated + 理由。**不在候选集里的 id 一律丢弃**（防编造规则）。

每次引用都写进 `rule_usages`，所以「命中次数」是真的统计，不是模型说的。

## 8.5 窄栏模式（浏览器右侧那一栏）

服务起来之后，同一个进程同时支持两种形态，**不需要第二个端口、第二个数据库**：

| 形态 | URL |
|---|---|
| 宽屏（默认） | `http://localhost:8501/` |
| 窄栏 | `http://localhost:8501/?embed=true&narrow=1` |

### 为什么不是 `?embed=1`

`embed` 是 Streamlit 自己的保留参数：`?embed=true` 会进它的原生嵌入模式（隐藏 Deploy 和菜单）。
更关键的是，**它在送给后端的 query_params 里被整个吃掉** —— Python 一侧读不到，
`st.query_params.get("embed")` 永远是 `None`。这是实测出来的，不是猜的。

所以两个参数各管一件事：

- `embed=true` → 交给 Streamlit，隐藏它自己的按钮；
- `narrow=1` → 我们自己的开关，决定布局。`side=1` / `panel=1` 是它的别名。

### 窄栏做了什么

1. **砍壳**：隐藏 header、toolbar、彩虹条、状态块、侧边栏及其折叠按钮、MainMenu、footer。
2. **砍空**：内容区 padding 从 6rem 级压到 0.5–0.7rem，纵向 gap 0.5rem，分割线 margin 9px。
3. **压字号**：根字号 16→14px，正文 13.5px/1.72，标题逐级下调，caption 11.5px。
4. **不溢出**（这条最重要）：`pre` 和 `pre > code` 强制 `white-space: pre-wrap`。
   Streamlit 的代码块里，`code` 元素自带 `white-space:pre` + `display:inline-block` + 内容宽度，
   只压 `pre` 会变成"文字被裁掉"，不是折行。
5. **气泡**：藏掉头像（省 40px 横向），助手气泡灰底左边框、用户气泡淡蓝底左边框 —— 头像没了也要分得清谁在说。
6. **触控**：按钮最小高 34px，expander 头也是。

### 列布局：代码分支，不是 CSS 硬掰

Streamlit 在 640px 以下会给每个 `stColumn` 加 `min-width: calc(100% - 21px)`，
**等于把一切列无条件竖排** —— 420px 下连两颗按钮并排都做不到。
窄栏 CSS 里把这条下限解开了，然后由代码决定每屏怎么排：

```python
from ui import layout
layout.narrow()                 # 当前是不是窄栏
layout.cols(2)                  # 窄栏 → 竖向堆叠；宽屏 → st.columns(2) 原样
```

具体到每一屏：四格标尺 4→2×2、待办/决策行 5 列→标题行+动作行、
「#N 疑点 · 依据 / 这条我允许」三列→两颗并排、下一步胶囊 4 颗→每行 2 颗、
澄清页的槽位面板收起成 expander、各页大标题隐藏（顶部选项卡已经有同名项）。

### 自检

```bash
python data/audit.py     # 420 / 480 / 1600 三个宽度逐屏截图 + 断言（横向溢出、裁切、同行按钮数）
python data/apptest.py   # 两种模式下 AppTest 跑到底，并验证窄栏不渲染侧栏导航
```

`audit.py` 的判定线：`documentElement.scrollWidth <= clientWidth + 1`、
没有 `scrollWidth > clientWidth` 的段落/代码块、420px 下同一行不超过 2 颗按钮。

## 8.6 桌面挂件（双击就能用的那个窗口）

### 三种形态，同一份数据

| 形态 | 入口 | 适合 |
|---|---|---|
| 宽屏 | `python -m streamlit run app.py` | 一次性把结果卡从头翻到尾 |
| 窄栏 | 同上，地址加 `?embed=true&narrow=1` | 用浏览器，但想省地方 |
| 桌面挂件 | 双击 `启动-桌面挂件.bat` | 常驻屏幕侧边，随时复制粘贴 |

三者共用一个 Streamlit 进程、一份 `data/app.db`。挂件启动时先探活 8501：
已经在跑就直接复用（不重启、不动你当前的会话）；没跑才在后台静默拉一个，
关窗时只收掉自己拉的那个。

### 窗口能干什么

- 默认 **400 × 800**（按屏幕 DPI 换算成物理像素；这台 200% 屏上是 800 × 1600）
- **无边框**：顶部一条 28px 极简边框，中间抓手、右边三颗按钮（置顶 / 最小化 / 关闭）
- **整条可拖**：抓顶部任意空白处拖
- **四边四角可缩放**：鼠标移到边上会变成缩放光标
- **默认置顶**：点图钉可取消/恢复
- **记住位置尺寸**：关窗写进 `data/gadget.json`，下次原地打开
- 重复双击不会开出第二个，会把你已有的那个顶到前面

### 为什么是 pywebview 不是 Qt

PySide6 的 `startSystemMove()` / `startSystemResize()` 是系统级调用，拖动缩放手感
与原生窗口完全一致，本来更省心。但代价是 150MB+ 依赖，且 QWebEngine 要独占一份 Chromium。

pywebview 复用系统已装的 WebView2，只多 1MB 依赖、内存与 Edge 共享。
代价是无边框窗口的所有细节都得自己补 —— 下面三条是补的时候撞出来的。

### 三个必须知道的坑

**1. `frameless=True` 会把 `resizable` 覆盖掉。**
pywebview 里 `resizable` 先设、`frameless` 后设，后者把窗口样式整个换掉，
`WS_THICKFRAME` 就没了，窗口不可缩放。得在 `shown` 之后用 Win32 把它加回去。

**2. WebView2 是独立子窗口且铺满客户区。**
鼠标在窗口内部按下时消息发给 WebView2，**根本不经过本进程窗体的 WndProc**，
所以对客户区返回 `HTCAPTION` 是空转，窗口纹丝不动。窗口边缘那圈非客户区除外 ——
这就是为什么四边缩放能靠系统原生工作，拖动不行。

最终让页面里的 `mousedown` 通过 js_api 回来，Python 侧 `SetCapture` 把鼠标消息
从 WebView2 抢过来，再按光标位移 `SetWindowPos`（顺带避免拖动时选中页面文字）。
也试过在回调里发 `SendMessage(WM_SYSCOMMAND, SC_MOVE)` —— 一秒内就返回、窗口不动，
因为 js_api 回调不在 GUI 线程上，系统不认这个跨线程移动请求。

**3. WebView2 的 `devicePixelRatio` 不等于窗口 DPI。**
窗口 DPI 是 192（缩放 2.0），但 WebView2 报的 `devicePixelRatio` 是 2.38：
给 800 物理宽的窗口，页面 `innerWidth` 只有 327 CSS px。启动后实测校准一次
（`Shell.calibrate`），用真实 `innerWidth` 反推「物理/CSS」比，命中区和标题条高度
都按这个值算，不按 DPI 硬算。327px 下窄栏布局站得住（`scrollWidth == clientWidth`）。

**4. 双击 `.bat` 挑到了机器上另一个 Python（`ModuleNotFoundError: No module named 'webview'`）。**

本机 PATH 里还有一份 Python 3.12 住在用户目录（`C:\Users\<user>\pythonw.exe`，
正是 `py` 启动器的默认目标，`sys.prefix` 就是家目录），它排在项目用的 3.13 前面，
没装 pywebview。`where pythonw.exe` 只认名字，先命中的就是它 —— 于是双击后弹
「启动时崩了」，而命令行里 `python desktop_app.py` 却是好的（`where` 顺序不同，
或 shell 的 PATH 被改过），问题只在 Explorer 环境复现。

现在 `data/find_python.bat` 按**能力**而非名字挑解释器：对每个候选先跑一次
`-c "import streamlit,webview"`，退出码 0 才采用。候选顺序是项目 `.venv`（若将来建了）、
`where pythonw.exe` / `where pyw.exe` 的**全部**结果、`.workbuddy\binaries\python\versions\*`
下每个版本、常见安装路径。三个启动脚本（挂件 / 窄栏 / 宽屏）都 `call` 它，解析结果
落在 `PY`（python.exe）和 `PYW`（pythonw.exe）两个绝对路径变量里。

`desktop_app.py` 另加一道 `check_deps()`：启动即把 `sys.executable` 写进日志，缺包时
弹窗写明「是哪个解释器缺什么」和「哪条命令能修」，不再甩裸 traceback。

## 8.7 审阅分支（一条待办 = 一支对话）

以前所有事挤在一条对话流里：你在同一个输入框里既要问"整体行不行"，又要处理"第 3 条待办"，
说着说着就不知道自己在聊哪件事了。现在把它们拆开：

```
主干：结论 + 原文 + 委托卡   ← 只读底座，随时退回来
  ├─ 分支 #1 补做移动端真机测试   （独立对话，只聊这条）
  ├─ 分支 #2 补一份内容维护说明
  └─ 分支 #3 先修移动端还是先补部署步骤
```

主干上是一排**分支入口卡**（标题 + 一行摘要 + 几轮对话/未开）。
点一张卡 = **换一屏**，不是展开。327px 的窄栏里放不下"左列表 + 右对话"，
分栏只会把对话压成一行四个字，所以走换页。

### 数据长什么样

| 表 | 变化 |
|---|---|
| `branches`（新） | 一支一行：来源条目、标题、问题、锚点偏移、`state`、结论、合并时间、消息数 |
| `messages` | 加一列 `branch_id`。**空 = 主干**，老数据天然全归主干，不需要迁移脚本 |

关键约束只有一条：**`list_review_messages(review_id)` 默认只返回主干**，
要看全部必须显式 `with_branches=True`，要看某一支必须点名 `branch_id`。
这是踩着"会话分裂"那个 bug 的教训定的 —— 平铺一个 `branch_ref` 列，
11 个查询点漏一个就串台，而且不报错，只有用户觉得"我没说过这句"时才发现。

分支在第一次打开审阅页时自动物化（`materialize_branches`，按 `(review_id, finding_id)` 幂等），
老评审不需要迁移。

### 上下文怎么给（3 万字原文不塞给模型）

四层，总共 3500 字上限：

| 层 | 内容 | 预算 |
|---|---|---|
| ① 委托卡 | 目标 / 交付物 / 每条验收标准 / 禁止项 | **不截断**（缺一条就答偏） |
| ② 锚点窗口 | 这条 `quote` ±500 字 + detail/选项 | ≤1200 字 |
| ③ 全文骨架 | 段号 + 每段首句，锚点所在段标 ★ | ≤800 字 |
| ④ 分支历史 | 最近 6 轮，每条 ≤300 字 | ≤900 字 |

超预算时裁剪顺序固定：**远历史 → 骨架段数 → 锚点窗口**，委托卡永远不动。

全文不是不给，是**按需取**：分支页有「在原文里找…」，检索结果先渲染给你看，
你点「把第 N 段带进对话」才进下一轮上下文。**扩不扩上下文，决策权在你手里，不在模型手里** ——
模型不能自己喊"我需要更多"就把 3 万字拉进来。

每支底部挂一张**上下文回执**（折叠）：

```
委托卡 58 字 · 锚点 1013 字（原文第 11210–12223 字）· 骨架 30 段 866 字 · 历史 6 轮 108 字
合计 2045 字 ≈ 2.0k tokens ｜ 已省略全文其余 28301 字
```

这是"拒绝黑箱"最实在的一块：模型凭什么这么说，能一路查到它当时看见了什么 ——
**包括它没看见的那部分**。

### 合并：一件事只留一个真相源

「标记完成并合并到主干」之后，主干时间线多一行灰字，结论同时进「补充说明」：

| 分支类型 | 条目状态 | 主干得到什么 |
|---|---|---|
| 决策 | 保持 `decided`，**不覆盖**你选过的选项 | `分支「…」已合并：结论` |
| 待办 | 新状态 `merged`，`chosen` 存结论 | 同上 |
| 手工分支（`free`） | 不动任何条目 | 同上 |

两条刻意的判断：

- **不复用 `followed`。** 它现在的语义是"已开新会话"（分叉会话），
  拿来表示"已合并"会让两种完全不同的动作共用一个状态，以后复盘分不清。
- **合并不可逆**（用户 2026-11-08 拍板）。合并后分支只读、不能再聊，
  要重开就回主干再开一支。只有一个真相源，比"允许反悔"少一半状态机。

### 分支 ≠ 分叉会话

|  | 分支（8.7） | 分叉会话（第 5 节） |
|---|---|---|
| 在哪 | 审阅页内部，换一屏 | 工作台，新会话 |
| 上下文 | 自动带委托卡 + 原文锚点 | 要重新澄清 |
| 适合 | "把这一条想清楚" | "这一条要单独做成一个产物" |
| 状态 | `branches.state` | `findings.state='followed'` |

两个入口都留着。主干卡片上是「聊这一条」，分支页里藏着一颗「开成独立会话」。

### 防迷失的四条

1. 路由条位置和高度永不变（`← 主干` 在左，"分支 i / N"在右）。
2. 永远显示"第几支 / 共几支"。
3. 分支页顶部一行"只讨论这一条 · 待办 · 未合并"，每次进出都重申边界。
4. 主干卡片带状态（未开 / 3 句 / 已合并）—— 主干那个进度是**你自己挣来的**，
   不是模型给的百分比。

### 自检

```bash
python data/seed_branch_demo.py      # 铺一条带 3 支的演示评审（打开就能点）
python data/branchtest.py            # 隔离性 / 预算 / 合并回写 / 降级，32 项断言
python data/uitest_branch.py         # AppTest 真点一遍：进分支→聊→回主干→换支→合并
python data/audit_branch.py 8501     # 400 / 480 逐屏量：不溢出、同行 ≤2 颗按钮
```

`branchtest.py` 用确定性 fixture（不起服务、不联网、不走 LLM），
因为隔离和预算要的是精确数字，不是"看起来对"。

### 已知限制

- 分支只在审阅页里。把它搬进工作台（跨阶段带着走）没做。
- 锚点是按字符偏移取的，Agent 输出里如果是超长单段（几千字不分段），
  骨架会退化成一两段，此时 ②层就是全部视野。
- 手工分支（`free`）没有锚点，上下文只有委托卡 + 骨架 + 历史，模型容易答得比较泛。

## 9. 几条工程约定（这版为什么这么写）

- **`session_state` 只放 `session_id` 和纯界面态**。业务状态一律从 SQLite 读。刷新页面不丢东西，
  换浏览器也能接着用同一个会话。
- **确定性不听模型的**。模型自评之后，还要跟客观事实取低者：跳过的槽位、未锚定的疑点都会压级，
  卡片上写明“模型自评确定，已下调为存疑”。
- **完成度不是模型给的百分数**，是成功标准逐条判定（达标 1 / 部分 0.5 / 未达标 0）加权算出来的。
  点开「成功标准逐条」能看到每条的判定依据。
- **规则不会自动生成后直接生效而无人知晓**：从驳回理由提炼的规则当场展示在页面上，
  立刻可编辑 / 归档 / 删除，来源标为「来自驳回」并记着是哪次评审。
- **模型返回不是 JSON 就不断流程**：先自动修复重试一次；仍失败则把原始返回摊开给你看，
  流程不崩。贴回结果这一步不会因为模型抽风而作废。
- **会话要能被信任**：建会话失败不留空壳，模型挂掉不留孤零零的用户发言，
  输入框按会话隔离。这三件事任一失守，历史就会看起来“分叉”，你就没法判断自己走到哪一步了。
- **草稿比控件活得久**：存在库里，不靠 `session_state`（控件一卸载就被清）。
- **待办/决策和疑点同源**：同一个 `findings` 表、同一套锚定、同一套折叠交互，
  不为了新功能另起一套，否则追溯会分裂成两套标准。
- **模型负责说话，不负责决定按钮能干什么**：对话里的意图解析只允许引用候选集里的
  `finding_id`，`option_label` 必须逐字等于某个选项；接受/驳回这类不可逆动作，
  还要用户原话里真的出现“接受/驳回/不收”这些词才执行。按钮（胶囊）则完全由状态算出来。
- **对话不是第二套历史**：审阅消息复用 `messages` 表，只是多了 `review_id` 和
  `phase='review'`。一旦另起一张表，刚修好的“历史分裂”会以另一个名字回来。

## 10. 已知限制（别当成完成品）

- **演示替身不是 AI**：没配 Key 时，澄清只是“把你这句话塞进当前缺的槽位”，结果卡是按规则拼出来的。
  它能证明**追溯和规则机制是真的**，但不能证明判断质量。要真实判断必须配 Key。
- 不做长文本切分。超过上限（默认 30000 字）会要求你先裁剪 —— 越长，锚点定位越容易失手。
- 一条规则只用一个 `text` 字段，没有版本历史；改了就改了（引用记录仍指向 id）。要追溯规则演变的话这版不够。
- 单用户、无权限、无并发保护（本地单机假设）。
- 审阅对话在演示替身下只是“骨架 + 连接词”，语气不会真的像人；
  真实模型才会把它说成一段话。但**结构、锚定、规则沉淀在两种模式下是同一条路径**。
- 意图理解靠模型 + 关键词双闸门：模型判成「驳回」但你原话里没写驳回，就不会执行，
  只在回复里提示你点胶囊。宁可少做，不会替你做。
- 待办/决策的质量完全取决于模型。演示替身给的是固定样例；真实模型偶尔会把“已做完的事”
  写成待办，或把有标准答案的事写成决策 —— 提示词里已经明令禁止，但不是 100% 可靠。
  看到不合理的条目，直接驳回并在理由里写清楚，它会变成规则。
- 不接工作 Agent 的 API、不自动执行、不替你拍板。
