# 修改计划 · 审阅对话改造为「多分支平行交互」

> 目标：把「一条待办 = 一个需要用户想清楚的小问题」从一条混在一起的对话流里拆出来，
> 变成一条主干 + N 个隔离分支。主干负责"看懂全局"，分支负责"想清楚这一条"。
>
> 不改的东西：委托卡、结果程度卡、接受/驳回/改方向三道闸门、规则库。
> 分支是**加法**，砍掉任何现有能力的方案都不接受。

---

## 0. 一句话定性

| 层 | 内容 | 谁写 |
|---|---|---|
| 主干 | 委托卡快照 + Agent 原文 + 开场白 + 结案动作 | 系统生成，用户只能读和结案 |
| 分支 | 一条待办/决策 + 它想清楚的过程 + 一句结论 | 用户和模型一来一回 |
| 合并 | 把分支结论写回主干时间线，并进入「补充说明」 | 用户点按钮，代码执行 |

产品上这意味着：**用户永远不需要在"理解全局"和"处理细节"之间二选一**，
因为全局一直是只读锚点，细节则是可随时进出的沙盒。这就是"外骨骼"和"更强的 Agent"的区别。

## 1. 现状盘点与改造量（先给结论）

- `messages` 表已经是"多用途"的：`review_id` + `phase` + `kind` + `refs_json`，

## 2. 数据模型（问题 1 的答案）

### 选型：`branches` 表 + `messages.branch_id`，不用单列 `branch_ref`

三个理由，按重要性排：

1. **分支有生命周期，不只是个标签。** 开 → 聊 → 合并/放弃 → 结论回写。
   `branch_ref` 只能回答"这句话属于谁"，回答不了"这一支处理完了吗、结论是什么、什么时候合的"。
   塞进 `messages` 就要么加 5 个列（`branch_state/branch_resolution/branch_merged_at`…），
   要么每次靠聚合 `messages` 现算 —— 后者会让"读一条分支"变成一次全表扫 + GROUP BY。
2. **一次「会话分裂」的教训。** 当初的 bug 是父会话和子会话共享行、靠 `parent_*` 追血缘，
   结果一个查询忘了带条件，历史就串了。**平铺的 `branch_ref` 是同一个坑的翻版**：
   11 个调用点里漏掉一个 `WHERE branch_id IS NULL`，分支对话就会漏进主干。
   有独立表 + 单一入口函数（见下）才能把"漏条件"变成"编译期就写不出来"。
3. **一个分支可以比它的来源条目活得久。** 用户可能在决策已经定下之后，还在这一支里追问
   "为什么推荐这个"；也可能手工开一个"我还没想清楚"的空分支。`finding_id` 只作为可空外键。

### DDL

```sql
CREATE TABLE IF NOT EXISTS branches (
    id          TEXT PRIMARY KEY,               -- BR-<8hex>
    review_id   TEXT NOT NULL REFERENCES reviews(id) ON DELETE CASCADE,
    finding_id  INTEGER,                        -- 来源条目；可空（手工开的分支）
    kind        TEXT NOT NULL,                  -- action_item | decision | doubt | risk | free
    title       TEXT NOT NULL,
    question    TEXT NOT NULL DEFAULT '',       -- 这一支到底要解决什么（用户可改）
    quote       TEXT,                           -- 绑定的原文锚点
    char_start  INTEGER,
    char_end    INTEGER,
    state       TEXT NOT NULL DEFAULT 'open',   -- open | merged | dropped
    resolution  TEXT NOT NULL DEFAULT '',        -- 合并时的一句话结论
    merged_at   TEXT,
    msg_count   INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_branches_review ON branches(review_id);

-- messages 只加一列。旧行全为 NULL ⇒ 天然全部归主干，零迁移风险。
ALTER TABLE messages ADD COLUMN branch_id TEXT;   -- 走 MIGRATIONS 列表（幂等 try/except）
CREATE INDEX IF NOT EXISTS idx_messages_branch ON messages(branch_id);
```

### 隔离铁律（这是本方案的核心约束）

**唯一入口，默认主干，分支必须显式点名。**

```python
def list_review_messages(review_id, branch_id=None):   # None = 主干（branch_id IS NULL）
def list_branch_messages(branch_id):                   # 只给分支用
```

不允许出现 `list_review_messages(rid)` 拿到"全部"。要全部得写 `transcript_text(rid, with_branches=True)`。
这样"忘了过滤"的后果从"串台"变成"拿不到" —— 能立刻在页面上看出来。

`review_chat.respond` / `narrate.ensure_opening` / `transcript_text` 三个调用点全部跟进。

### 迁移策略

- 表：`CREATE TABLE IF NOT EXISTS`，老库直接建。
- 列：追加到 `MIGRATIONS` 列表，`_migrate` 已有 try/except，重复执行为空操作。
- 分支物化：`materialize_branches(review_id)` 幂等 —— 按 `(review_id, finding_id)` 查重，
  老评审第一次打开审阅页时自动补出分支，不需要数据迁移脚本。
- 回滚：删 `branches` 表 + 忽略 `bridge_id` 列即可，旧代码读 `messages` 不受影响。

## 3. 上下文组装（问题 3 的答案，重点）

### 原则：不是"少给模型"，是"按相关性分三层给"

3 万字全塞：超 token、贵、慢，而且模型会被无关段落带偏（长上下文里"注意力稀释"是真实存在的）。
只给锚点：模型不知道这份东西整体长什么样，会答出"建议整体重构"这种废话。

所以分四层，各层有独立预算：

| 层 | 内容 | 预算 | 是否截断 |
|---|---|---|---|
| ① 委托卡 | goal / deliverable / 每条验收标准 / forbidden | 400–800 字 | **不截断**。这是"目标与边界"，缺一条就会答偏 |
| ② 锚点窗口 | 该分支 `quote` ±500 字 + finding 的 detail / options / recommended | ≤1200 字 | 不够时退到 ±200 |
| ③ 全文骨架 | 按空行切段，每段给「段号 + 首句 40 字 + 字数」，锚点所在段标 ★ | ≤800 字 | 超 30 段只留段号 + 首句 20 字 |
| ④ 分支历史 | 最近 6 轮，每条 ≤300 字；更早的压成一行「你已确认：…」 | ≤900 字 | 先砍最远的 |

总预算 **3500 字**（中文粗估 1 字 ≈ 1 token，约 3.5k 输入 token），硬上限 5000。
超限时的裁剪顺序固定：**远历史 → 骨架段数 → 锚点窗口 800→400 字**，永远不砍委托卡。

### 关键补充：全文不是不给，是"按需取"，而且先给用户看

用户迟早会问"原文里到底有没有提到 X"。两个动作：

1. **「在原文里找这句」**：拿用户这句话里的关键词（复用 `rules.derive_keywords`）在
   `results.raw_output` 里做包含匹配，取命中密度最高的 3 个窗口，**先渲染在页面上给用户看**。
2. 用户看完点「把这段也带进对话」，才把选中的窗口追加进下一轮的 ②层。

区别很重要：**上下文扩不扩，决策权在用户手里，不在模型手里。**
模型不能自己说"我需要更多上下文"就把 3 万字拉进来 —— 那不是辅助，那是替用户做主。

### 可追溯：上下文回执

每轮请求后，分支页底部挂一个折叠的「这次给模型看了什么」：

```
委托卡 620 字 · 锚点 1180 字（原文第 1420–2600 字）· 骨架 24 段 780 字 · 历史 5 轮 640 字
合计 3220 字 ≈ 3.2k tokens ｜ 已省略：全文其余 27400 字
```

这不是装饰。产品边界写着"所有判断必须可追溯、拒绝黑箱"，那"模型凭什么这么说"
就得能一路查到它当时看见的原文 —— 包括它**没**看见的那部分。

## 4. UI 拓扑（问题 2 的答案）

### 约束先说清

挂件 400 逻辑宽，实测 CSS 只有 **327px**（WebView2 的 devicePixelRatio 2.38 那个坑）。
327px 里放不下"左边列表 + 右边对话"两栏 —— 任何分栏方案都会把对话压到 200px 以内，
一句话折成四行。所以拓扑必须是**换页**，不是分屏。

### 三态 + 一条常驻路由条

```
┌─ 400px ───────────────────────────────┐
│  ← 主干   审阅 · 待决定            ⋯  │  ← 常驻路由条（唯一固定元素）
├───────────────────────────────────────┤
│ 完成度 78%  确定性 中  偏差 小         │  ① 数字条
│                                       │
│ 我仔细看了一遍……（开场白人话）        │  ② 开场白（含 #2 #3 编号）
│ 「#2 待办 · 补移动端真机测试」        │
│                                       │
│ 可以单独拉出来处理的 3 件事            │  ③ 分支入口卡区
│ ┌───────────────────────────────────┐ │
│ │ ② 待办  补移动端真机测试      3 句 │ │
│ │   只在 iOS 真机上复现过            │ │
│ └───────────────────────────────────┘ │
│ ┌───────────────────────────────────┐ │
│ │ ③ 决策  先修排版还是先补内容  未开 │ │
│ └───────────────────────────────────┘ │
│                                       │
│ 接受 / 驳回 / 打包成补充说明（胶囊）   │  ④ 主干动作
│ [ 对审阅专家说……            ] [发送]  │  ⑤ 主干输入（问整体问题）
└───────────────────────────────────────┘
              │ 点卡片 = 换页（不是展开）
              ▼
┌─ 400px ───────────────────────────────┐
│  ← 主干   分支 2/3          [✓ 完成]  │  ← 同一条路由条，位置不变
├───────────────────────────────────────┤
│ 只讨论这一条 · 待办                    │  ⑥ 分支身份条（一行，防止迷失）
│ 目标：给社团做一个报名页… ▾            │  ⑦ 委托卡摘要（折叠，默认收起）
│ 原文：「只在 iOS 真机上复现」 ▾        │  ⑧ 原文锚点（折叠，点开看上下文）
│ ─────────────────────────────────────  │
│ 你：安卓上也试过？                     │  ⑨ 分支对话（只有这一支）
│ 侧车：试过两台，没复现……              │
│                                        │
│ 上下文 3.2k 字 ▾                      │  ⑩ 上下文回执（折叠）
│ [ 说说这条怎么弄……          ] [发送]   │
│ [ 在原文里找这句 ]                     │  ⑪ 检索兜底
│ [ 标记完成并合并到主干 ]               │  ⑫ 合并（主按钮）
└───────────────────────────────────────┘
```

### 路由与状态

- 路由只用 `st.session_state[f"branch::{rid}"]`：为空 = 主干，否则 = 该分支。
  **不进 URL** —— `?embed=true&narrow=1` 已经被 WebView2 占着，再加参数会和 Streamlit 的
  `embed` 保留参数打架（上一轮踩过）。
- 「← 主干」只做一件事：把 key 置空 + `st.rerun()`。分支对话不丢，因为都在库里。
- 合并成功后自动回主干，主干时间线多一条灰字 `分支 ②「…」已合并：结论一句话`。
- 分支被合并/放弃后，卡片仍留在主干（划掉 + 结论），因为"处理过什么"本身是信息。

### 反迷失的四条硬规则

1. **路由条位置和高度永不变**（40px）：从主干进分支，只有条上的文字变。用户的肌肉记忆不会错位。
2. **永远显示 `分支 i / N`**：知道"还有几件没处理"，就不会觉得掉进无底洞。
3. **分支顶部一行「只讨论这一条 · 待办」**：每次进入都在重申边界，防止用户在分支里问全局问题
   （真问了也不拦，但模型会先答这一条，再提示"要不要回主干问"）。
4. **主干卡片带状态**：`未开 / 3 句未完成 / 已合并`。主干的"完成度"是这 N 张卡片的进度，
   不是模型给的百分比 —— 这是唯一一个**用户自己挣来的**进度指标。

## 5. 合并语义（产品上最容易被忽略、技术上最容易写坏的一处）

「标记完成并合并到主干」到底发生什么：

| 分支类型 | 条目状态 | 分支状态 | 主干得到什么 |
|---|---|---|---|
| decision | 保持 `decided` + `chosen=选项` | `merged` | 一行 note：`分支 ③「先修排版还是先补内容」已合并：先修排版` |
| action_item | `merged`（新增状态，不用 `followed`） | `merged` | 一行 note：`分支 ②「补真机测试」已合并：已在 iPhone 13 上复现` |
| 结论为空 | 拒绝合并，提示"先写一句结论" | 不变 | 无 |

两条关键判断：

- **不能复用 `followed`。** 它现在的语义是"已开新会话"（`fork_from_finding`）。
  拿来表示"分支已合并"，两种完全不同的动作会共用一个状态，以后复盘分不清。
- **条目状态和分支状态解耦。** 决策在分支里选定后，条目就已经是 `decided`；
  合并只是"这一支聊完了"，不该把 `decided` 覆盖成别的值。

合并后的结论进入 `build_followup`，排在"已排除 / 已定 / 还欠的"之后，新增一段：

```
4. 下面几条我们已经聊清楚了，按结论执行：
   - 补真机测试 → 已在 iPhone 13 上复现，安卓不复现，按 iOS 兼容处理
```

**这是分支架构真正的价值兑现点**：用户不用自己把 8 段分支对话手工总结成一段话，
结论自动汇进那份"甩给 Agent 的补充说明"。

### 分支 ≠ 分叉会话（要跟用户说清楚，也要在 UI 上分开）

| | 分支（本方案） | 分叉会话（已有 `fork_from_finding`） |
|---|---|---|
| 在哪 | 审阅页内部 | 工作台，新会话 |
| 上下文 | 自动带委托卡 + 原文锚点 | 要重新澄清 |
| 适合 | "把这一条想清楚" | "这一条要单独做成一件事/一个产物" |
| 状态 | `branches.state` | `findings.state='followed'` |

两个入口都保留，但主干卡片上主按钮是「聊这一条」，`开成独立会话` 收进 `⋯` 菜单。

## 6. Prompt 组装（`core/prompts.py` 新增）

```python
BRANCH_REPLY_SYSTEM = """你是「认知掌控侧车」的审阅专家，现在只跟用户讨论一件事。
用户从结果卡里单独拎出了这一条，其他条目暂时都不用管。

你会拿到四样东西：
1. 委托卡（目标、交付物、验收标准、禁止项）—— 这是边界，任何建议都不能越界；
2. 原文锚点（这一条对应的那段 Agent 输出）—— 你的判断只能基于它；
3. 全文骨架（段号 + 每段首句）—— 只用来说明"这件事在全文的哪个位置"，不许据此推断细节；
4. 这一支的对话历史。

硬约束（违反会被系统丢掉）：
1. 只回答这一条。用户问别的，先答完这一条，再提示"要不要回主干问"。
2. 引用原文必须逐字，不许改写、不许拼接两句；原文里没有的，就说没有。
3. 不重复整张卡的结论，不复述委托卡 —— 用户已经看过了。
4. 每句 60 字以内。不用 markdown 标题/列表/加粗。
5. 你只能建议，不能替用户决定；要用户拍板的地方，把两条路的代价各说一句。

只输出 JSON：
{"say": "……", "intents": [{"type": "answer|decide|conclude|none",
  "option_label": "", "resolution": ""}], "suggest": "一句话"}
"""
```

`intents` 的四个类型与执行权：

| type | 谁能触发 | 代码做什么 |
|---|---|---|
| `answer` | 模型判断 | 只记对话，不改任何状态 |
| `decide` | 模型判断 + `option_label` 必须逐字命中 | 写 `findings.state='decided', chosen` |
| `conclude` | **关键词闸门**（"就这么办/我确认了/结论是"）+ 用户原话 | 只生成 `resolution` 草稿，**不自动合并**，等用户点按钮 |
| `none` | 兜底 | 记对话 |

沿用现有哲学：模型负责"听懂"，改状态必须过代码闸门，不可逆动作必须用户明说。

## 7. 验收（`data/branchtest.py`，四组断言）

1. **隔离性**
   - 建 2 个分支，各说 2 句 → 主干 `list_review_messages` 只看到主干消息（数量不变）
   - 分支 A 的 `list_branch_messages` 里不含分支 B 的任何一行
   - `transcript_text(with_branches=True)` 能按分支分组输出
2. **预算**
   - 塞 3 万字原文 → 组装结果总字数 ≤ 3500，且委托卡 0 裁切
   - 锚点窗口确实落在 `char_start±500` 内，且 `★` 标在正确段
   - 逐级超限时裁剪顺序为 历史 → 骨架 → 锚点
3. **合并回写**
   - decision 分支合并后：`findings.state` 仍是 `decided`（没被覆盖）、`branches.state='merged'`
   - action_item 分支合并后：`findings.state='merged'`、结论进入 `build_followup` 文本
   - 结论为空时合并被拒绝，且数据库无任何写入
4. **降级**
   - 模型 500/超时 → 分支里也留一行"没理解"的 failure 消息，不丢用户输入（沿用现有 `respond` 的兜底）
   - `branches` 表不存在时（老库未迁移）审阅页不崩，退化为纯主干

另加：`data/audit.py` 的窄栏断言扩展到分支视图（420/480px 下 `scrollWidth <= clientWidth + 1`；
分支页同行按钮 ≤ 2）。

## 8. 三处最容易出事的地方

| 风险 | 后果 | 防线 |
|---|---|---|
| **R1** 某个调用点漏了 branch scope | 分支对话漏进主干（"会话分裂"同族 bug，且更难发现，因为不报错） | 单一入口 + 默认主干 + `branchtest` 的隔离性断言 |
| **R2** 迁移不幂等 | 第二次启动 `duplicate column name: branch_id`，应用起不来 | 走 `MIGRATIONS` 的 try/except；表用 IF NOT EXISTS；连续 init 两次的断言 |
| **R3** 合并把条目状态写坏 | 决策的 `chosen` 被清空、待办误标 `followed`，规则统计跟着错 | 状态解耦（§5 表格）+ `merged` 新状态 + 合并前校验结论非空 |

回滚方案：`branches` 表可整表删；`messages.branch_id` 留空列不影响旧代码；
`ui/page_review_chat.py` 的分支视图可以靠一个 `BRANCHES_ENABLED = False` 开关一键关掉，
关掉后就是今天的行为。

## 附：这套设计对产品定位的三处兑现

1. **保护理解权**：主干永远是只读锚点，用户随时能退回去看全貌，不会"进了分支就忘了全局"。
2. **保护决策权**：上下文带多少由用户勾选（§3），不合并到主干就不合并（§5），
   模型只给建议 + 代价，不给命令。
3. **拒绝黑箱**：每个分支能看到"模型这次看了哪 3220 字、漏掉了哪 27400 字"（§3 回执）——
   这是这套架构里最不像"功能"、但最像"产品主张"的一块。
