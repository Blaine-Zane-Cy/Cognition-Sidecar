# 修改计划 v2 — 对话连续性、结果卡分支、草稿保全

> 本文档只做评估与方案，不含代码改动。确认后再实施。

## 0. 结论先行（含一处与你判断不一致的地方）

三处升级里，**只有第二处（待办/决策分支）需要动数据模型**。第一处叫「对话历史分叉」，但我用你的真实库（`data/app.db`）和真实浏览器逐项复现后，结论是：

**分叉不在 `messages` 表里，也不在 `st.chat_message` 渲染里，而在会话边界上。** 如果按字面去改 messages 表结构和聊天渲染，改完现象不会消失。

三条实证：

### 证据 1 — 会话级孤儿（数据层，来自你的 `data/app.db`）

7 条会话里有 4 条（19:51–19:57）**只有 brief、没有任何问答**，且 brief 内容高度重复：

```
19:51:35  clarifying  我要做一个认知掌控的侧车，帮我避免因为认知局限导致的后续任务…
19:54:19  clarifying  做一个认知掌控侧车，帮我了解agent的输出结果，避免因为个人局限…
19:55:59  clarifying  帮我做一个网页，展示我的成果
19:57:57  clarifying  做一个个人网站，展示我的研究方向
```

机制在 `core/flow.py:14`：`start_session()` **先** `db.create_session()` **再** `ask()`。模型调用一失败，会话行已经落库，但 `st.session_state["session_id"]` 从未被赋值 —— 界面退回起始表单，你只能把同一段构想再写一遍，于是同一需求被劈成多条互不相识的会话。

### 证据 2 — 消息级孤立（代码层）

`flow.submit_answer()` 先写用户消息，再调模型。`ask()` 抛异常时，库里留下一条**没有对应问题**的用户发言。再发一次就变成 `user, user, assistant` —— 渲染出来是「两句话粘在一起，只回答了一个问题」，这就是肉眼看到的断层。两次写入分属两个独立的 SQLite 连接，没有回滚。

### 证据 3 — 跨会话串味（浏览器实测，最像「分叉」）

`ui/page_workbench.py:115` 的 `st.form("answer")` 用的是**全局固定 key**。两个会话都在澄清阶段时，切换会话并不会卸载这个输入框。实测：

```
A 里输入框值: 这是A的回答，我还没发
切到 B
B 页面 textarea 值: ['这是A的回答，我还没发']
→ A 的草稿是否跟着跑到 B: True
```

在 A 里写、在 B 里发，回答直接落进 B 的会话。这才是「对话历史分叉」最具体的一种。

### 反过来，实测证明「本来就好的部分」

| 检查项 | 实测结果 |
|---|---|
| 聊天块数是否随 rerun 重复追加 | 1 → 3 → 5 → 7，与 DB 行数（8 行含 brief）**完全一致**，没有重复 |
| 切到 B 再切回 A，A 的历史是否完整 | 完整，3 个气泡；B 的内容未混入 |
| 消息顺序是否稳定 | 稳定（`ORDER BY id`，秒级时间戳不参与排序） |

所以：**你要的验收标准我照做**（同一 session 多轮问答只对应一条连续记录、rerun 不追加新块），但我加一条前提 —— 渲染层必须**锁死为「每次 rerun 从 DB 全量重绘」**。现在正是这样做的，升级后不能为了做分支面板把历史塞进 `session_state`，那才会真的产生追加块。

## 1. 升级一：对话历史连续性

### 1.1 目标（可核查）

1. 一次建模失败**不再**产生孤儿会话：要么完整建成，要么标记为 `aborted` 并在下拉里隐藏。
2. `messages` 表里 user / assistant **严格交替**；失败也占一格（写一条 `kind='failure'` 的说明），不留孤立发言。
3. 输入框按会话隔离：A 的草稿不可能出现在 B 的输入框里。
4. 渲染永远是 DB 全量重绘，`session_state` 不存任何消息。

### 1.2 `messages` 表结构改动

```sql
ALTER TABLE messages ADD COLUMN round_no INTEGER NOT NULL DEFAULT 0;  -- 第几轮问答
ALTER TABLE messages ADD COLUMN kind ...
ALTER TABLE messages ADD COLUMN anchor_hint TEXT DEFAULT '';          -- 预留：这条问题在问哪个槽位
CREATE INDEX idx_messages_session_round ON messages(session_id, round_no);
```

- `round_no` 回填规则：按 `id` 升序遍历，每遇到一条 `role='user'` 就 +1（`brief` 记 0）。迁移脚本幂等。
- 不加 `turn_id`：`(session_id, round_no)` 已经唯一定位一问一答，多一列只是多一个会不同步的东西。
- **`kind` 扩展**：`brief | question | chat | note | failure | system`。`failure` 用于承载模型调用失败，让失败也进入对话流而不是消失。
- 排序仍用 `id`，`round_no` 只用于分组与「第 N 轮」标注，不参与排序 —— 避免同秒同 round 时排序抖动。

### 1.3 目标形态（这就是「一条连续记录」长什么样）

```
id  round  role       kind      content
1   0      user       brief     做一个个人网站，展示我的研究方向
2   1      assistant  question  这个网站做完之后，最主要是给谁看？
3   1      user       chat      给研究生导师和同方向的人看的…
4   2      assistant  question  做完时你手里具体拿到什么？
5   2      user       chat      一个能直接打开的静态页面，加一份说明文档
6   3      assistant  failure   这一次没跑通（模型返回不是 JSON）。你的回答已存下，点「重试上一步」继续。
7   3      user       chat      （用户的回答）
8   4      assistant  note      信息够了，我按这些内容生成委托卡。
```

`user` 后面必定跟一条 `assistant`（`question` / `note` / `failure` 三选一）。这条不变量是「不分叉」的定义。

### 1.4 三个文件的改法

**`core/db.py`**
- 新增 `_migrate()`：`PRAGMA table_info` 检查缺列再 `ALTER TABLE`，在 `init_db()` 里调用。幂等，老库无损升级。
- 新增 `add_exchange(session_id, round_no, assistant_text, kind)`：**一个连接、一个事务**写 assistant 消息（用户消息由 `submit_answer` 在同一轮内先行写入并立即返回 id，配对关系由 `round_no` 保证，不依赖跨事务）。
- 新增 `next_round(session_id)`：`SELECT COALESCE(MAX(round_no),0)+1`。
- 新增 `list_sessions(include_aborted=False)`：默认过滤 `stage='aborted'`。
- 新增 `mark_aborted(sid)` / `abort_empty_sessions()`（把已存在的 4 条孤儿批量标 aborted，只跑一次，跑前备份）。

**`core/flow.py`**
- `start_session()`：`try: ask(sid) except: db.mark_aborted(sid); raise`。`start_session` 失败后 UI 不再拿到 sid，且那条会话不会污染下拉。
- `submit_answer()`：写用户消息 → `try: ask(sid) except: db.add_exchange(..., kind='failure', ...); raise`。失败也补一格 assistant，保证交替。
- `ask()`：所有 `db.add_message` 调用统一带 `round_no`。
- `ensure_delegation` 失败时同理（写 `failure` 而不是静默）。

**`ui/page_workbench.py`**
- `_session_bar()`：selectbox **给显式 `key="sess_pick"` + `on_change` 回调**，回调里把选择写进唯一真相 `session_id`，并清理该页所有 `UI 临时态`（`answer_*` / `revise_*` / `paste_*` / `skip_*` / `reason_*`）。删除「render 期间根据 widget 返回值覆盖 `session_id`」的写法 —— 那是 Streamlit 明确不推荐的路径，也是状态不同步的唯一入口。
- 所有输入控件 key 带会话维度：`f"answer_{sid}"`、`f"revise_{sid}"`、`f"paste_{sid}"`。
- 新增 `_transcript(sid)`：唯一的消息渲染函数，`db.list_messages(sid)` → 逐条 `st.chat_message`。`failure` 用灰色警示块 + 「重试上一步」按钮；`note` 用弱化样式。**禁止任何 form 之外的追加逻辑。**

## 2. 升级二：结果卡里的待办 / 决策分支

### 2.1 为什么复用 `findings` 而不新建表

待办和决策条目同样需要「可追溯」这条铁律（锚回原文片段 or 某条规则）。`findings` 表已经有 `quote / char_start / char_end / match_type / match_score / rule_id` 全套，复用它等于白拿锚定、白拿折叠渲染、白拿导出。新建 `branches` 表要重写这三样，是本项目里最不该重复的代码。

代价：`findings` 语义从「发现」变宽为「挂在某张卡下的一条结构化条目」，靠 `kind` 区分。可接受。

### 2.2 数据模型

```sql
-- findings.kind 扩展为: sub_goal | doubt | risk | action_item | decision
ALTER TABLE findings ADD COLUMN options_json TEXT NOT NULL DEFAULT '[]';  -- decision 的分支
ALTER TABLE findings ADD COLUMN recommended TEXT NOT NULL DEFAULT '';     -- decision 推荐哪一项
ALTER TABLE findings ADD COLUMN why TEXT NOT NULL DEFAULT '';             -- 为什么推荐
ALTER TABLE findings ADD COLUMN state TEXT NOT NULL DEFAULT 'open';       -- open|revisited|decided|followed|skipped
ALTER TABLE findings ADD COLUMN chosen TEXT NOT NULL DEFAULT '';          -- 用户点下的那一项

-- 有意的分叉要留血缘，否则和"缺陷分叉"分不开
ALTER TABLE sessions ADD COLUMN parent_review_id TEXT;
ALTER TABLE sessions ADD COLUMN parent_finding_id INTEGER;
```

`core/models.py` 新增：

```python
FINDING_KINDS = ("sub_goal", "doubt", "risk", "action_item", "decision")
BRANCH_KINDS = ("action_item", "decision")
BRANCH_STATE_LABELS = {"open": "待处理", "revisited": "已回溯",
                       "decided": "已选", "followed": "已开新会话", "skipped": "已跳过"}
ANCHOR_LABELS = {"exact": "逐字命中", "fuzzy": "近似匹配",
                 "rule": "引用规则", "unanchored": "未锚定"}
```

### 2.3 Prompt 升级（`core/prompts.py`，REVIEW_SYSTEM 增补）

在现有 7 条硬约束后追加两条，并把新字段写进 JSON 契约：

```
8. action_items：Agent 没做、但用户下一步必须自己做的事。每条 title 用动词开头（≤18 字）。
   不允许把 Agent 已经做完的事写成待办。0~4 条，没有就返回空数组。
9. decisions：存在两条以上互斥路线、且选择权在用户手里的地方。0~3 条，没有就返回空数组。
   有标准答案的事不许写成决策。每个 option 必须写代价。

所有 action_items / decisions 与疑点同样受第 1 条约束：
quote 必须是从 Agent 输出里原样复制的连续片段（5~60 字），不得改写、不得拼接。
如果这条待办/决策在原文里确实没有对应句子，quote 返回空字符串 —— 系统会把它标为"未锚定建议"，
移出首屏，但不会因此下调整张卡的确定性。
```

JSON 契约追加：

```json
"action_items": [{"title": "补做移动端真机测试", "detail": "为什么这是待办",
                  "quote": "原文逐字片段或空串", "rule_id": null, "severity": "high|medium|low"}],
"decisions": [{"title": "先修排版还是先补内容", "why": "两句方向互斥",
               "options": [{"label": "先修排版", "cost": "内容仍是空的，演示价值低"}],
               "recommended": "先修排版", "quote": "原文逐字片段或空串"}]
```

### 2.4 `core/review.py` 的改法

- 新增 `_collect_branches(raw, text, threshold, cand_ids)`，对每条的 `quote` 走同一个 `anchoring.locate()`，产出与疑点同构的 dict。
- **确定性口径不变**：只有 `doubt` / `risk` 的未锚定数量参与 `unanchored_count` 与降级。待办/决策未锚定只打标，不压级 —— 理由：待办不是「结论」，让它在证据上失分没有道理；而结论失分是为了防止你被无依据的判断带走。
- 限额：`action_items` 入库 ≤4，`decisions` ≤3（`MAX_BRANCHES`）。
- `db.add_finding(...)` 传入新字段；`list_findings` 返回时展开 `options_json`。

### 2.5 首屏面板（`ui/components.py` 新增 `render_branches`）

位置：**四格标尺之下、疑点之上**。理由：30 秒决定时，「下一步做什么」比「哪里不对」更靠前。

结构（视觉稿见对话里的示意图）：

```
┌ 待处理分支 ─────────────────────────────────────────────┐
│ 待办 2 条 · 决策 1 条                                    │
│                                                          │
│ ☐ 补做移动端真机测试            [逐字命中]  回溯 · 以此新建 │
│ ☐ 补一份内容维护说明            [未锚定→折叠]              │
│                                                          │
│ ⌥ 先修排版还是先补内容          [近似匹配]  回溯 · 以此新建 │
│    推荐：先修排版 · 因为首屏空着等于没法给人看             │
│    ▸ 展开看 2 个选项与各自代价                             │
└──────────────────────────────────────────────────────────┘
```

具体规则：

- 首屏**只显示前 2 条待办 + 前 2 条决策**，其余进「还有 N 条（折叠）」。
- 每条**只露一行标题 + 锚点徽章**；点开 `expander` 才看 `detail` / 原文片段 / 规则依据。沿用疑点那套渐进披露，不做第二套交互。
- 未锚定的待办/决策：不进首屏，收进底部折叠区，标题加「未锚定」。
- 决策默认不展开选项：展开后是 2~4 个带代价的单选项 + 「记下选择」按钮。不预选，不自动提交。

### 2.6 两个按钮的行为定义

**「回溯」** —— 只读，不产生任何新实体。

1. `state='revisited'`（落库，便于回看时知道哪些被追过）。
2. 就地展开：显示 `_mark()` 高亮块，上下文各 120 字（比疑点的 70 字宽，因为回溯是想看清全貌）。
3. 结果卡页额外把「原文对照」tab 的高亮 span 加入这一条，并滚动定位（`st.session_state["focus_span"]` 只是 UI 临时态，允许放 session_state）。

**「以此新建会话」** —— 有意的分叉，必须留血缘。

1. `flow.fork_from_finding(finding_id)`：
   - 新 session：`brief` = `f"{finding.title}｜承接自 {原委托卡 goal}"`；
   - `parent_review_id` / `parent_finding_id` 落库；
   - `stage='clarifying'`，槽位预填 `goal`（用 finding 的 title）；
   - 写入一条 `kind='note'` 的系统消息：「本会话承接自 RV-xxx 的第 N 条待办/决策」。
2. 原 finding `state='followed'`。
3. UI：切到新会话，并在会话下拉里显示为 `… ｜承接自 rv-xxxx`。
4. **只允许在工作台触发**，结果卡回看页不给这个按钮 —— 回看是历史视图，不该能开出新枝。

> 这一条正是升级一与升级二容易互相打架的地方：升级一要消灭「缺陷分叉」，升级二要有「有意分叉」。区分手段就是 `parent_*` 两列 —— 没有 parent 的重复会话是缺陷，有 parent 的是设计。

### 2.7 替身与示例数据必须同步（否则演示当场断）

- `core/mock_llm.py::_review`：产出 2 条 `action_item`（1 条可锚定、1 条故意不可锚定）+ 1 条 `decision`（2 个选项）。连同已有的「锚定失败 1 条」「规则命中 1 条」，覆盖四种状态。
- `seeds/demo_data.py`：在示例 Agent 输出里补一句可被待办锚定的原话（例如「移动端适配留到下一轮」），让「1 条可锚定」成立。
- `demo.py`：新增两项自检 —— ① 待办/决策入库条数与各自 `match_type` 打印；② `fork_from_finding` 后新会话的 `parent_review_id` 正确回指。

## 3. 升级三：草稿保存与恢复

### 3.1 一个决定方案的实测事实

Streamlit 的 widget key 状态**随 widget 卸载被删除**。实测：

```
写入后 session_state: {'draft_x': '写了一半'}
切到 p2 后还有 draft_x 吗: False
切回 p1 后 textarea 值: ''
```

所以「把草稿放 `st.session_state` 就够」是错的 —— 页面一切走，key 就没了。`session_state` 里**非 widget 的普通 key** 能活，但那要靠 `on_change` 主动搬运，且浏览器刷新即丢。

**结论：草稿落 SQLite。** 理由不只是持久，还有：你切回工作台时应该看到「上次写到哪」，而不是一个空框加一句「请重新输入」。

### 3.2 `drafts` 表

```sql
CREATE TABLE IF NOT EXISTS drafts (
    scope      TEXT NOT NULL,     -- workbench / review
    key        TEXT NOT NULL,     -- brief | answer:s-xxx | paste:s-xxx | revise:s-xxx | reason:rv-xxx
    content    TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (scope, key)
);
```

### 3.3 捕获时机（双通道，必须两条都做）

| 通道 | 触发点 | 覆盖什么 |
|---|---|---|
| ① `on_change` | 每次输入框失焦/提交时 | 正常输入路径（text_area 的值由前端在 blur 时提交） |
| ② 渲染前镜像同步 | 每次 rerun 开头，读 `st.session_state[widget_key]` 与 DB 比对，不同则写库 | **输入后不点任何按钮、直接点侧栏导航**的竞态 |

通道②是必须的：点导航会先让 widget 卸载，若只有 `on_change`，最后几个字可能还没提交就被丢弃。实现放在 `app.py` 顶部（每 run 执行一次 `drafts.sync_pending()`），一个函数扫一遍已知草稿 key 前缀即可。

### 3.4 回填

`ui/components.py` 新增 `draft_input(label, scope, key, ..., height, placeholder)`：

1. 首渲染：`st.session_state.setdefault(widget_key, drafts.load(scope, key))`。
2. 之后只传 `key`，**不再传 `value`** —— 同时给两者会触发 Streamlit 警告与覆盖。
3. 挂 `on_change=lambda: drafts.save(scope, key, st.session_state[widget_key])`。
4. 提交成功后 `drafts.clear(scope, key)`，否则下次进来还残留上一次的内容。

覆盖的输入点：`brief`（新构想）、`answer:{sid}`、`revise:{sid}`、`paste:{sid}`、`reason:{review_id}`。

### 3.5 清理与体量

- 设置页加「清空草稿」按钮 + 显示草稿总字数。
- `paste:{sid}` 单条上限 20000 字（与结果粘贴上限 30000 分开算，草稿只是防丢失，不做权威存储）。
- 提交成功后立刻删，避免 DB 随使用膨胀。

## 6. 风险点与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 迁移不可逆 | 现有 7 条会话 / 规则库报废 | 只做 `ADD COLUMN` 加列，不改类型不删列；跑前 `cp data/app.db data/app.db.bak`；迁移函数幂等可重跑 |
| **首屏膨胀**（本次最大风险） | 疑点 3 + 待办 2 + 决策 2，30 秒决定失效，直接违反验收标准 2 | 硬限额：首屏 2+2；每条只露一行标题；决策选项默认收起；给一条可核对的指标 —— 首屏可见行数 ≤ 8 行 |
| 未锚定的待办被当成结论 | 破坏「侧车不能是黑箱」 | 未锚定不进首屏，进底部折叠区并打「未锚定」标；且不参与确定性降级（口径变更要写进 `certainty_note` 文案，避免你误以为降级变松了） |
| 「以此新建会话」制造新分叉 | 升级一刚修好，升级二又开一堆会话 | `parent_*` 两列必填 + 下拉标注「承接自」+ 仅在结果卡待决策状态可用；无 parent 的重复会话一律视为缺陷 |
| 草稿 blur 竞态 | 最后几个字丢 | 双通道捕获（`on_change` + 渲染前镜像同步）；验收动作必须是「不点按钮直接切页」 |
| `value=` 与 `key` 同时给 | Streamlit 警告 / 覆盖用户输入 | 只在首渲染 `setdefault`，之后只传 `key` |
| 真实模型产不出合规 `action_items` | 首屏空白，功能形同虚设 | 契约里允许空数组；UI 显示「本轮无待办」而不是空白；`mock` 保证演示路径始终有内容 |
| `findings` 语义变宽 | 后续统计（`unanchored_count`、疑点计数）串味 | 所有统计显式带 `kind` 过滤；`json` 导出加 `kind` 维度的分组计数 |
